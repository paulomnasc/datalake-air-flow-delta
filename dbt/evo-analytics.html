1. Visão Geral da Mudança Estratégica

Este documento orienta a reestruturação da camada de negócios analítica do MyDataFlow. O nosso pipeline principal de processamento do Data Lakehouse (ingestão e transformações pesadas da Bronze à Gold) já está homologado e roda de forma altamente escalável via código no S3/MinIO utilizando a classe medallion_pipeline_v2.py orquestrada pela Dag Factory.

Esta evolutiva acopla o ecossistema moderno de dados (Modern Data Stack) focado estritamente em Governança, Linhagem (Lineage Graph), Testes de Qualidade de Dados e Modelagem de Cubos DW. Centralizaremos as definições dimensionais no PostgreSQL analítico (banco datalake_bi), consumido de forma rápida e segura pelo visualizador Metabase.

2. Alinhamento Arquitetural (Explicação Técnica Analítica)

Para alinhar o entendimento do time de desenvolvimento, reproduzimos o detalhamento de como a stack opera de ponta a ponta e o papel de cada componente, definindo claramente a separação de responsabilidades e evitando retrabalho do pipeline existente:

Como funciona a Engenharia e Modelagem Dimensional Lógica

O dbt substitui a classe medallion_pipeline_v2.py?

Não. O processamento pesado de arquivos colunares Parquet no S3 continua sob responsabilidade exclusiva da Dag Factory e do medallion_pipeline_v2.py. O papel do dbt na nossa arquitetura é puramente lógico e declarativo. Ele entra na ponta final sobre o banco analítico Postgres para mapear a linhagem e formatar as views para o BI.

  • Dag Factory & medallion_pipeline_v2.py (O Storage / Motor do Lakehouse): Processa os arquivos RAW e grava Parquets no S3/MinIO.
  • DAG de Sincronização (sync_delta_to_postgres.py) (O Transportador): Copia as tabelas Gold estruturadas do S3/MinIO para o schema public do PostgreSQL analítico.
  • dbt Core (O Maestro / A Camada de Governança): Lê as tabelas Gold sincronizadas no schema public do Postgres, roda os testes de integridade, gera a linhagem visual (Lineage Graph) e materializa as dimensões e fatos finais no schema analytics.
  • Metabase (Os Olhos / O Frontend): Conecta no PostgreSQL, mapeando estritamente as tabelas geradas no schema analytics do dbt para alimentar gráficos e dashboards de forma ultra-rápida.

O Fluxo de Processamento de Dados na Prática (Pipeline ELT)

3. Plano de Implantação Passo a Passo

O desenvolvedor deverá executar o provisionamento e configuração seguindo estritamente as etapas abaixo:

Fase 1Inicialização, Dependências e Sandbox Lógico

O dbt operará via CLI local no host, isolado em um ambiente virtual Python para não poluir o sistema:

  1. Adicionar dependências no requirements.txt: dbt-core>=1.5.0 e dbt-postgres>=1.5.0.
  2. Instalar dependências no ambiente virtual Python executando o script automatizado: ./install_dbt.sh.
  3. Configurar o arquivo profiles.yml contendo isolamento lógico de segurança:
    • Target dev: Aponta para o schema homolog_analytics no Postgres (parquinho de testes).
    • Target prod: Aponta para o schema analytics no Postgres (produção/Metabase oficial).
  4. Implementar a macro macros/generate_schema_name.sql para garantir que o dbt execute o roteamento direto e limpo de cada ambiente de execução sem concatenar nomes de forma indesejada.

Fase 2Modelagem Lógica Declarativa e Testes

Toda a modelagem dimensional deve ser declarada como arquivos SQL na pasta models/ do dbt:

  • dim_usuarios.sql: Mapeamento lógico de clientes com perfil comportamental a partir da tabela customers.
  • dim_cursos.sql: Mapeamento de produtos e cursos a partir da tabela products.
  • fato_vendas.sql: Consolidado de transações derivado de orders.
  • fato_acessos.sql: Consolidado de acessos diários derivado de activity_logs.
  • Configurar validações básicas e integridade analítica no arquivo schema.yml (ex: chaves primárias unique e not_null).
Nota de Engenharia — Rodando o Pipeline dbt

Para testar localmente no schema de homologação, execute: dbt run --profiles-dir . --target dev. Para validar as regras de integridade nos dados de teste: dbt test --profiles-dir . --target dev. Em produção oficial, utilize a flag --target prod.

Fase 3Implantação e Configuração do Metabase

O Metabase é implantado via Docker Compose sob a imagem oficial fixada metabase/metabase:v0.50.4 na mesma rede interna airflow_net do banco analítico.

Configuração de Portas nos Ambientes (.env):

  • Dev/Local: Declarar METABASE_PORT=3000.
  • Produção: Declarar METABASE_PORT=28300 (porta alta para evitar qualquer conflito no host de produção da AWS).

O docker-compose utilizará o mapeamento dinâmico "${METABASE_PORT:-3000}:3000", garantindo segurança total e isolamento.

4. Governança, Linhagem e Próximas Implementações

Com o dbt configurado, execute o comando dbt docs generate --profiles-dir . seguido de dbt docs serve --profiles-dir . --port 8001. Isso renderizará a documentação web interativa contendo o gráfico de linhagem (Lineage Graph) que ilustra de forma transparente o caminho das tabelas desde a sua cópia inicial do lakehouse até a entrega visual no Metabase.

Esta arquitetura unificada de governança garante escalabilidade e facilidade nas alterações analíticas, mantendo o controle sob controle de versão (Git) e sem afetar a robustez do pipeline de dados orquestrado pela Dag Factory.

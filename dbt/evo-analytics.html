2. Alinhamento Arquitetural (Explicação Técnica Analítica)

Para alinhar o entendimento do time de desenvolvimento, reproduzimos o detalhamento de como a stack opera de ponta a ponta e o papel exato de cada componente, desfazendo mitos sobre a substituição de motores de bancos relacionais por frameworks analíticos:

Como funciona a Engenharia e Modelagem Dimensional Desejada

O dbt substitui o PostgreSQL?

Não, o dbt (Data Build Tool) não vai substituir o seu PostgreSQL. Na verdade, eles trabalham juntos, como parceiros inseparáveis. A divisão clara de papéis na nossa stack é definida como:

  • PostgreSQL (O Motor / O Músculo): Continua sendo o seu banco de dados físico, onde os dados de fato ficam armazenados no disco rígido. É ele quem cede o poder de processamento, a memória e guarda as tabelas físicas.
  • dbt (O Maestro / O Cérebro): Ele não guarda dados. Ele é o framework que você usa para comandar o PostgreSQL. Em vez de você entrar no banco e criar tabelas ou views na mão usando SQL bruto, você escreve a lógica no dbt, e ele vai até o PostgreSQL e cria a estrutura dimensional (os cubos/tabelas estruturadas) de forma organizada, testada e documentada.
  • Metabase (Os Olhos / O Frontend): É a sua camada de visualização. Ele se conecta no seu PostgreSQL (especificamente nas tabelas de Fato e Dimensão que o dbt organizou por lá) e exibe os gráficos e dashboards bonitos para o usuário final de maneira ágil.

O Fluxo de Processamento de Dados na Prática (Pipeline ELT)

[Dados Brutos / Origem] (Logs de Atividade, APIs Hotmart)
          │

[PostgreSQL (Camada RAW / Bronze)]  ───► O dbt entra aqui, lê o RAW, processa e cria...
          │

          │
          ▼
[Metabase (Frontend Analítico)]     ◄─── Lê as tabelas limpas e entrega os cubos visuais.

Essa é uma excelente dúvida de quem está acostumado com a cultura do Docker, onde costumamos centralizar todas as variáveis de ambiente, usuários e senhas dentro do `docker-compose.yml`. No entanto, o **`profiles.yml` não fica dentro do Docker Compose**. Ele é um arquivo de configuração próprio e exclusivo do ecossistema do dbt. Aqui está a explicação de onde ele vem, por que ele existe e como ele se conecta ao seu Docker: --- ### 1. De onde vem esse arquivo? O `profiles.yml` é gerado automaticamente na sua máquina (ou dentro do container) no momento em que você executa o comando **`dbt init`** para começar um projeto. Por padrão, o dbt cria esse arquivo em uma pasta oculta no diretório do seu usuário no sistema operacional: * No Linux/WSL/Docker: `~/.dbt/profiles.yml` * No Windows: `C:\Users\SeuUsuario\.dbt\profiles.yml` Ele funciona como o **"gerenciador de conexões"** do dbt. É nele que você diz: *"Olha dbt, o meu ambiente de 'dev' aponta para o Postgres local na porta 5432, mas o meu ambiente de 'prod' aponta para o Redshift ou Athena na AWS"*. --- ### 2. Por que ele não fica direto no `docker-compose.yml`? Por uma questão de **segurança** e **arquitetura**: 1. **Isolamento de Credenciais:** O seu projeto dbt (os códigos SQL, as tabelas fato e dimensão) vai ser dropado dentro de um repositório Git. Você **nunca** deve subir senhas de banco de dados para o Git. Como o `profiles.yml` fica guardado fora da pasta do projeto (na pasta do usuário `~/.dbt/`), você evita o risco de expor suas senhas por acidente. 2. **O dbt roda fora do banco:** O `docker-compose.yml` serve para o Docker saber como levantar o contêiner do PostgreSQL e do Metabase. O dbt é apenas um cliente (como se fosse o DBeaver ou o PGAdmin) que vai se conectar neles. Ele precisa do seu próprio arquivo de configuração para saber onde o banco está rodando. --- ### 3. Como integrar o `profiles.yml` com o seu Docker Compose? Para o desenvolvedor que vai implementar, existem duas formas elegantes de fazer isso rodar em harmonia com o Docker: #### Abordagem A: Passando as variáveis do Docker para o `profiles.yml` (Mais Recomendada) Você pode criar o `profiles.yml` e deixá-lo ler as credenciais diretamente das variáveis de ambiente que o seu Docker Compose injetar. O dbt aceita Jinja (a engine de template do Python) para ler variáveis de ambiente. O arquivo `profiles.yml` do desenvolvedor ficaria assim: ```yaml meu_projeto_dbt: target: dev outputs: dev: type: postgres host: localhost user: "{{ env_var('DB_USER') }}" # Puxa o usuário do ambiente do Docker pass: "{{ env_var('DB_PASSWORD') }}" # Puxa a senha do ambiente do Docker port: 5432 dbname: data_lakehouse schema: analytics threads: 4 ``` #### Abordagem B: Mapeando por Volume no Docker Se você for rodar o dbt dentro de um container Docker (orquestrado pelo Airflow, por exemplo), você pode simplesmente criar o `profiles.yml` na sua máquina local e mapeá-lo como um volume dentro do service do dbt no seu `docker-compose.yml`: ```yaml services: dbt_runner: image: ghcr.io/dbt-labs/dbt-postgres:1.5.0 volumes: - ./meu_projeto_dbt:/usr/app/dbt - ~/.dbt:/root/.dbt # Mapeia a pasta do perfil para dentro do container environment: - DB_USER=${DB_USER} - DB_PASSWORD=${DB_PASSWORD} ``` ### Resumo da ópera: O `docker-compose.yml` levanta a infraestrutura (Postgres). O `profiles.yml` é o crachá de acesso que o dbt usa para conseguir entrar nessa infraestrutura e criar os cubos.

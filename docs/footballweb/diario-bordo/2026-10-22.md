# Diário de Bordo - 22/10/2026

## Filtro Canônico de Metas Diárias: Apenas Apostas Confirmadas com Débito a partir de 22/10/2026

---

### 1. Motivação e Diagnóstico Técnico

1. **Falha de Lógica de Negócio em Metas Diárias:**
   - O modelo `MetaDiariaModel.php` consultava a tabela `apostas` filtrando apenas por `status NOT IN ('Cancelada', 'CANCELADA')`.
   - Com isso, apostas geradas ou sugeridas pelos pipelines autônomos (como a DAG de cartões ou handicap) que ainda constavam como não confirmadas (`confirmada = 0`, status `Não Confirmada` ou `Pendente` sem lançamento de débito na conta corrente) estavam sendo precocemente agregadas às **Metas Diárias**:
     - Inflando a contagem de apostas cadastradas no dia;
     - Ocupando slots do **Ciclo Sequencial Ativo (Bloco de 10 Apostas)** antes mesmo da confirmação financeira pelo operador;
     - Poluindo os índices estatísticos de ROI, greens e reds projetados.

2. **Necessidade de Transição Segura com Preservação de Histórico:**
   - A tabela `conta_corrente` com a operação `DEBITO_APOSTA` foi implementada como parte da gestão de saldo de banca.
   - Aplicar uma restrição retroativa para exigir débito em conta corrente em datas passadas desconfiguraria os ciclos e dias arquivados antes da introdução da conta corrente.
   - Portanto, a regra estabelece uma linha divisória canônica (`DATA_CORTE_DEBITO = '2026-10-22'`):
     - Para datas de jogos/registro anteriores a 22/10/2026: preserva-se o histórico passado integralmente.
     - A partir de 22/10/2026 (hoje em diante): a aposta deve obrigatoriamente estar confirmada (`confirmada = 1`) **E** possuir débito efetivado na conta corrente (`tipo = 'DEBITO_APOSTA'`).

---

### 2. Arquivos e Trechos Modificados

1. **[`src/footballweb/app/Models/MetaDiariaModel.php`](file:///root/datalake-air-flow-delta/src/footballweb/app/Models/MetaDiariaModel.php)**:
   - Adicionada a constante de data de corte e o método canônico gerador de cláusula SQL:
     ```php
     public const DATA_CORTE_DEBITO = '2026-10-22';

     public function getSqlCondicaoApostaValida(string $aliasAposta = 'a'): string
     {
         $corte = self::DATA_CORTE_DEBITO;
         return "(
             DATE(DATE_SUB(COALESCE({$aliasAposta}.data_hora_jogo, {$aliasAposta}.criado_em), INTERVAL 3 HOUR)) < '{$corte}'
             OR (
                 {$aliasAposta}.confirmada = 1
                 AND EXISTS (
                     SELECT 1 FROM conta_corrente cc 
                     WHERE cc.aposta_id = {$aliasAposta}.id 
                       AND cc.tipo = 'DEBITO_APOSTA'
                 )
             )
         )";
     }
     ```
   - **`getProgressoDiario()`**: Inserida a condição `$condValida` na consulta leve de verificação de frescor e integridade (`$betCheck`).
   - **`recalcularCacheDiario()`**: Inserida a condição `$condValida` na agregação de totais cadastrados, liquidados, pendentes, greens, reds e retornos do dia.
   - **`getCicloSequencial()`**: Aplicado o filtro `$condValida` na montagem do ciclo sequencial (slots de 1 a 10).
   - **`getHistoricoCiclos()`**: Aplicado o filtro `$condValida` na partição dos ciclos históricos.
   - **`getHistoricoDias()`**: Aplicado o filtro `$condValida` na descoberta dos dias com apostas para geração de cache.

---

### 3. Impacto Prático e Regras de Negócio

* **Integridade das Metas Diárias:** A tela de metas diárias e os slots do ciclo agora refletem com fidelidade matemática apenas apostas reais em que houve compromisso de capital (débito debitado da conta corrente).
* **Fluxo de Confirmação:** Sugestões e apostas pendentes de confirmação permanecem visíveis na tela de apostas gerais, mas não impactam o progresso da meta diária ou o preenchimento de slots do ciclo ativo até que o usuário execute a confirmação com débito.
* **Preservação Histórica:** Todos os dias e ciclos finalizados em datas anteriores a 22/10/2026 continuam intactos e consistentes com seus registros originais.

## Atualização Emergencial de Segurança: Mitigação de RCE no PHP (CVE-2026-109618 e CVE-2026-109619 / "PHP2Shell")

---

### 1. Motivação e Diagnóstico Técnico

1. **Alerta de Segurança Hetzner Online & PHP Group (21/10/2026):**
   - Comunicação oficial da Hetzner notificando a publicação de atualizações de emergência do PHP Group referentes a duas vulnerabilidades críticas de Execução Remota de Código (RCE) não autenticada:
     - **CVE-2026-109618** (CVSS 9.2): Corrupção de memória durante tratamento de falta de memória (OOM) via `longjmp()`.
     - **CVE-2026-109619** (CVSS 9.2): Estado global obsoleto (*stale global state*) onde dados internos persistem após liberação de memória em erros fatais.
   - Ambas as falhas afetam diretamente interpretadores PHP atendendo requisições web via servidores web (Apache `mod_php`, PHP-FPM, etc.).

2. **Diagnóstico dos Ambientes no Servidor Dedicado:**
   - **Host (Ubuntu 24.04 LTS):** Executando CLI `php8.3-cli 8.3.6-0ubuntu0.24.04.12` (vulnerável).
   - **Aplicações Web Expostas à Internet via Nginx Gateway (Portas 80/443):**
     - `football-app` (`datalake-air-flow-delta-football-app`): rodando PHP 8.2.32 sobre Apache (vulnerável).
     - `fiscalweb` (`datalake-air-flow-delta-fiscalweb`): rodando PHP 8.2.30 sobre Apache (vulnerável).
     - `codeigniter-app` (`datalake-air-flow-delta-codeigniter-app`): rodando PHP 8.2.32 sobre Apache (vulnerável).
     - `lomadee-vitrine-webapp` (`lomadee-vitrine-vitrine-webapp`): rodando PHP 8.2.32 sobre Apache (vulnerável).
   - Por estarem diretamente expostas ao tráfego HTTP público, a atualização imediata era indispensável para neutralizar o vetor de ataque.

---

### 2. Ações Executadas e Infraestrutura Atualizada

1. **Host (Ubuntu 24.04):**
   - Atualizados os pacotes do PHP 8.3 via repositório de segurança oficial da Hetzner/Ubuntu (`noble-security`):
     ```bash
     apt-get install --only-upgrade -y php8.3*
     ```
   - Versão resultante: **`8.3.6-0ubuntu0.24.04.13`**.

2. **Imagens Docker das Aplicações Web:**
   - Efetuado o pull da nova imagem base oficial `php:8.2-apache` contendo o patch **PHP 8.2.35** lançado pelo PHP Group em 21/10/2026.
   - Reconstruídas as imagens das aplicações com reaproveitamento de cache para montagem das extensões (`pdo_mysql`, `pdo_pgsql`, `intl`, `gd`, `opcache`, `mysqli`):
     - `datalake-air-flow-delta-football-app`
     - `datalake-air-flow-delta-fiscalweb`
     - `datalake-air-flow-delta-codeigniter-app`
     - `lomadee-vitrine-vitrine-webapp`

3. **Reinicialização e Troca de Containers:**
   - Os containers das aplicações foram recriados e reiniciados sob a nova imagem sem interrupção de volumes ou bancos de dados relacionais (MySQL e PostgreSQL).

---

### 3. Impacto Prático e Regras de Negócio

* **Blindagem Total Contra RCE:** O servidor e todas as rotas públicas passam a operar sobre as versões com mitigação oficial do PHP Group (`8.3.6-0ubuntu0.24.04.13` no host e `8.2.35` nos containers), eliminando os vetores de corrupção de memória e persistência de ponteiros nulos.
* **Preservação de Código e Configurações:** Nenhuma regra de negócio, motor analítico (`cards_engine.py`, `asian_handicap_engine.py`) ou banco de dados sofreu alterações de estrutura. O Apache e o CodeIgniter mantiveram compatibilidade total.
